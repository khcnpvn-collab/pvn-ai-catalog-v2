# Review findings

- **P2 — The archive predicate does not establish that the item has no distinct record-level content.** `supabase/migrations/202610130006_deduplicate_partner_cooperation.sql:12-35` compares detail fields, source IDs, and relations, but never compares or constrains `records.summary`, `observed_on`, `source_note`, or `visibility`. Version 2 only shows that the item was migrated from the old kind; it does not prove those fields are redundant with the canonical record. An item with a distinct summary or source note passes and disappears from active dossiers. A visibility difference can also change which users see the remaining cooperation. The row and its audit are retained, so this is loss from the active view rather than physical deletion. The fixture in `scripts/tests/cooperation-deduplication-setup.sql:2-9` leaves these fields empty, and `scripts/tests/cooperation-deduplication-checks.sql:3-25` cannot detect this case. Add a guard for material record fields or an explicit, reviewed exemption for the 53 IDs; add a negative fixture.

- **P2 — The ADT member guard can accept the wrong two edges.** `supabase/migrations/202610130006_deduplicate_partner_cooperation.sql:75-88` requires two `partner` edges and independently finds workbook keys `DT0002` and `DT0003`, but the two `exists` clauses can resolve to the *same* target if that record has both source links. The second edge can point to an unrelated or archived record, and neither clause checks that the target is an active partner. The migration would then rename the group despite failing its stated two-member condition. Require distinct target IDs with active `partner` records, and test both positive and malformed groups; the added SQL fixture currently has no ADT group.

- **P2 — Eligibility can become stale before archive during an online migration.** `supabase/migrations/202610130006_deduplicate_partner_cooperation.sql:6-35,53-61` materializes eligible IDs without locking the records or their related rows, then inserts audit and updates by ID without rechecking eligibility. A concurrent edit or new document/relation after the temporary table is built can make an item unique while it is still archived. Lock affected records and serialize relevant writes, or revalidate immediately before the update with a failure if any candidate changed. The reported preflight and postcheck counts do not rule out this interleaving.
